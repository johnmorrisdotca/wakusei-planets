[English](../close-zoom.md)

`painted` の見た目の天体の地図は、赤道を一周して2048ピクセルです。ふつうの大きさの絵では、Fit の約2倍までくっきり見え、それより近づくとぼやけます。そのため `<wakusei-body>` は8倍で止まっていました。衛星の絵では、惑星は広い絵の真ん中の小さな円なので、8倍でも惑星は画面の3分の1ほどの幅しかありません。「どうして土星にこれ以上近づけないの？」という声が出たのは、そのためです。

いまは、天体ごとに**その天体自身の細かさ**が足りなくなるところまでズームでき、その限界を要素が知らせます。限界は天体ごとに違い、二つの仕組みが支えています。

1. **細かい地図のタイル。** 2048ピクセルの絵より細かい、パブリックドメインの地図がある天体では、見えている部分だけを、最大で一周16384ピクセルまでの地図タイルのピラミッドから天体にのせます。タイルはズームに必要なときだけ取得し、いらなくなったら手放します。
2. **汎用的な細かさ。** 地図が、どれほど細かくても、画面のピクセルより4分の1以上広く引き伸ばされるところでは、シェーダーがオクターブごとにノイズを重ねて、天体がのっぺりしないようにします。これは天体を実際に測った特徴ではなく、ノイズです。そのことは下で説明します。

## 天体ごとのズームの限界

ズームは絵の大きさに対する倍率です。ズーム1では、絵は真ん中から端まで `extent` 天体半径の範囲を映します (天体一つなら2.2、衛星の絵なら、いちばん遠い衛星や輪が届く範囲で、7〜70です)。円盤の幅は、絵の幅の `zoom / extent` 倍です。赤道を一周 `W` テクセルの地図を、幅 `D` CSS ピクセルの円盤にのせると、1テクセルは `π D / W` ピクセルの幅に見えます。

- **本物の細かさ**が足りなくなるのは、幅480ピクセルの絵で、1テクセルが **1.6 CSS ピクセル**より広くなるところです。汎用的な細かさがない、地図のある天体の限界はここです。
- **汎用的な細かさ**は、岩や氷の天体を**1.15倍**、やわらかい天体 (ガス惑星の縞、金星の雲、タイタンのもや) を**2倍**遠くまで運びます。輪の帯は、サンプルを一列に並べたものなので、**1.25倍**だけです。土星は、輪の細かさの限界まで行けます。
- どの天体も、上限は8倍を下回らず (陰影つきの見た目がいつももっていた値です)、1000倍を超えません。

タグの `zoom-min` と `zoom-max` は、これらすべてに優先します。タイルの組が見つかった天体は、範囲がタイルの許すところまで広がります (その要素のバーも追いかけます)。タイルの組が見つからなかった天体は、2048ピクセルの絵の許す範囲のままです。

## タイル

タイルの組は、天体の地図を、いくつかの大きさで512ピクセルの WebP の正方形に切ったものです。レベル `L` は幅 `2048 × 2^L` ピクセルで、`2^(L+2)` 列、`2^(L+1)` 行です。0列目は経度 -180、0行目は緯度 90 にあり、タイルは `<body>/<level>/<column>/<row>.webp` です (`<body>` は天体、`<level>` はレベル、`<column>` は列、`<row>` は行)。レベル0はパッケージ自身の2048ピクセルの絵で、切りません。`manifest.json` に、天体ごとに何があるかが書いてあります。

| 天体 | 最上位のレベル | 出典 |
|---|---|---|
| 火星 | 3 (16384) | バイキングの火星デジタル画像モザイク 2.1、カラー、1ピクセル1 km |
| 月 | 3 (16384) | LRO カメラのカラー地図 (NASA SVS、CGI Moon Kit) |
| 地球 | 3 (16384) | 地形と海底地形つきの Blue Marble Next Generation |
| 水星 | 2 (8192) | メッセンジャー MDIS の全球ベースマップ |
| イオ、カリスト | 2 | ガリレオとボイジャーのモザイク (NASA、USGS) |
| レア、エンケラドス、テティス、ディオネ、イアペトゥス | 2 | カッシーニの全球カラー地図 (NASA、JPL、SSI、LPI) |
| トリトン | 2 | ボイジャー2号のモザイク (ポール・シェンク、LPI) |
| 冥王星、カロン、ミマス | 1 (4096) | ニュー・ホライズンズとカッシーニのモザイク |

タイルは、**パッケージ自身の2048ピクセルの絵を引き伸ばしたものに、もとの画像の細かい部分を足したもの**です。もとの画像は、2048ピクセルの絵を作ったときと同じやり方 (同じ回転、同じ帯の投影、同じ彩度の落とし方) で球にのせ、2048ピクセルの絵にない細かさだけを、本当にデータがあるところに足します。だれも撮っていない極の黒い部分には足しません。だからタイルの色、色の調子、埋めた極は、どのレベルでも2048ピクセルの絵のままで、変わるのは鮮明さだけです。もとの画像のライセンスとクレジットは `NOTICE.md` にあります。

ガス惑星、金星、タイタン、ケレス、ガニメデ、エウロパ、太陽には、パッケージで使える、もっと細かい地図 (パブリックドメインのもの、またはライセンスを引き継げるもの) がないので、タイルはありません。2048ピクセルの絵と汎用的な細かさがその分を支えます。太陽は、いままでと同じように描かれます。

### 要素がすること

- ズームが初めて2048ピクセルの絵より細かいものを求めたとき、**タイルの組を一度だけ読みます** (`manifest.json`。ページ内のすべての要素で共有します)。タイルが必要になるまで、ほかは何も取得しません。
- カメラの枠と天体の極と本初子午線から、**見えている部分を求めます** (枠の中に極があれば、すべての経度が見えています)。**レベル**は、ズームとピクセル比から決めます。テクセルがデバイスピクセルより4分の1を超えて広くならない最小のレベル、なければいちばん細かいレベルです。
- **絵の窓を作ります。** 同じレベルのタイルを丸ごと、最大16枚 (2048ピクセル四方、または極のまわりの4096×1024のような帯) 集めて、シェーダーで地図の上にのせます。窓のふちは地図に溶けこみ、窓は経度180をまたげます。極をふくむ窓は、極にふちがありません。16枚より多く必要になる見え方 (幅の広い絵でズームが小さいとき、または極が入っているとき) は、ズームが大きくなるまで2048ピクセルの絵のままです。
- **見え方が落ち着くまで待ってから** (140ミリ秒) 取得します。ドラッグやピンチの途中で通りすぎるものは取得しません。同時に取得するのは最大6枚です。見えている範囲が窓の中にあるあいだは、窓を使い続けます。
- **必要なときだけ描きます。** 窓の準備ができると、1回の描画を頼みます。ほかの描画といっしょに毎秒30回までに抑えます。止まっているとき、画面の外にあるとき、隠れたタブのときは何も描かず、動きを減らす設定にしている人には、これによる動きは加わりません。
- **持っているものを手放します。** 必要がなくなった窓は4秒間 (すぐ戻るかもしれないので) 置いてから、窓の絵と、デコードしたタイルをすべて手放します。使っているあいだに持つデコード済みのタイルは最大48枚で、窓のものが優先です。
- **エラーを出さずにもとの絵に戻ります。** `tiles` のアドレスがない、manifest が読めない、タイルが取得できない場合は、天体は自分の絵で描かれ、取得できなかったタイルは30秒間は取り直しません。`element.stats.tiles` が、いまの状態 (`ready`、`level`、`shown`、`held`、`loading`、`failed`、`requested`、`pixels`) を、`element.stats.zoomMax` が範囲を伝えます。

### かかる負荷

| | |
|---|---|
| グラフィックスメモリ | 窓は一つで、ミップマップをふくめて、1チャンネル8ビットの2048ピクセル四方が最大です。**約22 MB**で、新しい窓を作る一瞬は、もう一つ分が必要です。パッケージの2048ピクセルの地図は、その下に残ります (これまでどおり約22 MB)。 |
| デコード済みのタイル | 最大48枚 (1枚約1 MB) で、ページのメモリを**48 MB**使います。窓といっしょに手放します。 |
| ネットワーク | 見えているタイルです。窓は最大16枚、1枚約20〜50 KB です。ズームしないページが取るのは、`manifest.json` (数 kB) だけです。 |
| キャンバス | 変わりません。キャンバスは絵の大きさで、レンダラーの上限 (1辺4096ピクセル、600万ピクセル) の中です。ズームしても描くピクセルは増えません。 |
| 端末 | メモリが2 GB 以下と答える端末 (`navigator.deviceMemory`) は、タイルを使いません。 |

## タイルの置き場所

タイルは **npm パッケージにも、リポジトリにも入っていません。** 15の天体で最大16384ピクセルまでだと約77 MB になり、リポジトリはすべてのファイルのすべての版を、ずっと残してしまうからです。タイルは `scripts/make-body-tiles.py` でもとの画像から作り、Pages のワークフローがビルドして、デモと並べて https://johnmorrisdotca.github.io/wakusei-planets/tiles/ から配信します (GitHub Pages は `access-control-allow-origin: *` を返します。公開リポジトリでは無料です)。

要素は、何も指定しなければそこを見にいきます。自分で絵を配信するページ (`texture-base` を指定するページ) は、場所を教えないかぎりタイルを使わないので、頼んでいないページから外へ出ていくことはありません。

```html
<wakusei-body body="mars" look="realistic" texture-base="/pictures/" tiles="/tiles/"></wakusei-body>
<wakusei-body body="mars" look="realistic" tiles="off"></wakusei-body>
```

自分で配信するには、作ってフォルダーをコピーします。

```sh
python3 -m venv .cache/venv && .cache/venv/bin/pip install pillow numpy
.cache/venv/bin/python -I scripts/make-body-tiles.py build
```

`pnpm tiles` は2行目を実行します。スクリプトは、もとの画像を一度だけ `.cache/body-tiles/` (git の対象外) にダウンロードし、SHA-256 がスクリプトに書いたものと違うファイルは使わず、もとの画像が2048ピクセルの絵に重なっているか (明るさの相関を、4分の1回転、半回転、4分の3回転ずらして調べます) を確かめて、`.cache/body-tiles-out/` に書き出します (数分かかります)。各レベルは、もとの画像全体から一度に作り、タイルごとには作りません。だから隣のタイルは境目で合い、経度180にも継ぎ目がありません。`pnpm test:tiles` は、テスト用の地図を切って、ピラミッドの形、各レベルが土台の色ともとの画像の細かさをもつこと、もとの画像にデータのないところに細かさが出ていないこと、タイルが継ぎ目なくつながることを確かめます。

## 汎用的な細かさ

地図の1テクセルが引き伸ばされ、画面の1ピクセルより4分の1ほど大きくなると、シェーダーは色にバリューノイズを重ねます。重ねるたびに大きさは半分になり、セルが2ピクセル以上あるあいだだけ重ねるので、画面に映らない細かさは出ませんし、ちらつきもしません。岩や氷の天体にはざらつきが、ガス惑星、金星、タイタンには、緯度の線に沿って伸びた、かすかなノイズ (点ではなく筋) が加わります。これは**ノイズであり、実際に測った特徴ではありません。** 同じ種類の天体ならどれでも同じで、クレーターでも嵐でもなく、のせている絵が足りなくなったところにだけ足します。地図が細かい天体ではノイズが少なく、光る天体 (太陽や恒星) には加わらず、ズームしても地図がくっきりしているなら加わりません。

シェーダーだけで描く天体 (`illustrated` の見た目と、地図のない衛星) は、クレーターや縞をどんな大きさでも数字から描きますが、描ける細かさには限りがあるので、4096ピクセルの地図として数えます。

## 土星の輪

輪は、カッシーニのモザイクから作った、C環の内側のふちからA環の外側のふちまでの2048個のサンプル (1つ30 km) の帯です。サンプルが1ピクセルの1.25倍より広くなるまではくっきり見え、それ以上では、帯より細かいノイズを半径方向に、重ねるたびに細かくしながら足して、細い輪 (リングレット) にします。帯のすきま (カッシーニの間隙、エンケの間隙)、色、輪への惑星の影、惑星への輪の影は、帯の値と幾何で決まるもので、これまでどおりです。輪のシェーダーは、テクセルが1ピクセルより小さいところでは絵を変えません。

## 変わらないもの

- `<wakusei-portrait>` は0.1〜8倍のまま、`<wakusei-space>` は100万分の1〜3倍のままです。どちらもペインター経由で2048ピクセルの絵を使って天体を描いていて、タイルの窓はまだありません。
- 移動は天体を絵の中に留めます (絵の中心が天体のふちから半径の半分より外へは出られません)。だから深くズームしているときは、円盤の外にある輪の部分は、移動では中心に置けません。円盤を横切る部分は置けます。
- レンダラーの上限 (1辺4096ピクセル、600万ピクセル)、毎秒30フレームまでの必要なときだけの描画、画面の外では何も描かないこと。`pnpm test:freeze` も、同じ限度で同じ確認をします。
